# PDF Craft v2.4.0

PDF Craft 2.4.0 is a major architectural and workflow release. It establishes native async
execution as the foundation of the SDK, introduces shared bounded capacity for remote OCR, LLM,
and JEV operations, evolves PCEX into a source-preserving multi-translation document, and adds a
review-and-repair pipeline for difficult footnotes. Together, these changes make large-book
conversion substantially more composable, responsive, and ready for provider-aware parallelism.

## Highlights

### An async-first SDK from extraction to rendering

- `AsyncPDFCraft` is now the primary integration surface for servers, notebooks, and other asyncio
  applications. OCR, translation, PCEX operations, Markdown/EPUB rendering, and PDF patching all
  follow native async orchestration, while `PDFCraft` remains the synchronous compatibility facade.
- Blocking filesystem, archive, OCR, Qt/PDF, renderer, and subprocess work runs in owned execution
  domains. Async callbacks stay on the caller's event loop, cancellation waits for safe teardown,
  and subprocess trees are reaped on success, failure, and cancellation.
- `PDFCraftExtraction` is now an opaque handle. Opening, exporting, translating, rendering, and
  patching go through `PDFCraft` or `AsyncPDFCraft`, keeping validation and I/O ownership at the
  public facade boundary.

See [#483](https://github.com/oomol-lab/pdf-craft/pull/483) and
[#484](https://github.com/oomol-lab/pdf-craft/pull/484).

### Shared, bounded concurrency for remote operations

- Add the public `AsyncExecutor` abstraction, `ConcurrentExecutor`, `FixedCapacity`, extensible
  capacity providers, and standard recoverable, rate-limited, and non-continuable operation errors.
- LLM translation, JEV review, footnote repair, and Vendor OCR can share an executor when they use
  the same provider quota, or use separate executors when their limits are independent. Retries
  release capacity before waiting and reacquire it for each remote attempt.
- PCEX and EPUB XML groups now run through one book-wide window, allowing work from different
  chapters to overlap. JEV page review and repair are concurrent, and Vendor OCR parallelizes only
  remote I/O while PDF rendering, result parsing, and page assembly retain their stable serial
  boundaries.
- Lazy operation production, bounded buffering, cancellation-safe teardown, and terminal-error
  propagation keep very large documents from eagerly materializing their full task set.
- Vendor failures now retain their original cause chain and distinguish rate limits, recoverable
  page failures, authentication or permission failures, and exhausted balance or quota. The
  default fixed-capacity provider bounds concurrency; provider-specific adaptive RPM/QPS control
  can be implemented through custom capacity providers.

### PCEX v4: source-preserving translation layers

- PCEX v4 keeps the source document unchanged and stores each translation as an independently
  identified layer with translated chapters, metadata overlays, coverage, and optional translated
  page furniture. Multiple translations, including multiple versions of the same language, can
  coexist in one `.pcex` file.
- New sync and async APIs list and resolve translation layers. `RenderMode.SOURCE`,
  `RenderMode.REPLACE`, and `RenderMode.BILINGUAL` deterministically compose source and selected
  translation content for Markdown and EPUB output.
- Translation selection is coverage-aware across metadata, headings, references, formulas, images,
  and tables. Display-formula bodies stay single in bilingual output while translated titles and
  captions remain available, and multi-fragment headings preserve their complete source ordering.
- PCEX translation now requires a known target language before any model call or output creation.
  Newly written archives use format v4; readers continue to accept v1, v2, and v3 archives.
- Anchored image/table translation validates XML structure, mixed-content slots, and formula
  identity before committing a layer. Structurally unsafe model output falls back to the source
  asset while valid siblings remain translated.

### JEV-assisted footnote refinement

- Add a reversible page-analysis boundary between traditional footnote resolution and chapter
  assembly. Existing algorithm-only behavior remains available and unchanged.
- `FootnoteOptions` and `FootnoteRefinement` expose three explicit tiers: disabled, traditional
  algorithm, and JEV-routed LLM refinement.
- The official async TypeSafe JEV SDK reviews pages with bounded concurrency. Only low-confidence
  pages enter constrained LLM repair, followed by deterministic validation that protects page
  structure, reading order, and source integrity.

See [#485](https://github.com/oomol-lab/pdf-craft/pull/485).

### More consistent translated output

- EPUB translation now keeps the table of contents, XHTML titles, book metadata, NCX title, output
  language, and archive members consistent across single- and multi-chapter books.
- XML fill preserves adjacent inline-formula placement, and independently translated image/table
  fields are rendered according to anchored coverage.
- PDF patching writes PCEX document metadata into standard PDF Info fields and preserves richer
  values in `/PDFCraftDocumentMetadata` when no standard field exists.
- Async LLM connectivity fallback, same-language Chinese preservation, and PDF patching for scans
  stored as full-page Stamp appearances receive dedicated regression coverage.

## Migration notes

- In code that already runs an event loop, construct `AsyncPDFCraft` and await its methods. The
  synchronous `PDFCraft` facade deliberately rejects calls from a running event-loop thread.
- Open and export `PDFCraftExtraction` through the Craft facades, then pass the opaque handle or a
  `.pcex` path back to facade methods.
- Supply an explicit shared `AsyncExecutor` for Vendor OCR and LLM-backed translation workflows.
  `ConcurrentExecutor(FixedCapacity(n))` is the straightforward fixed-concurrency implementation;
  XML `window` controls ordered look-ahead separately from provider capacity.
- Supply `target_language` when the translator does not declare one. Use `translation_id` to select
  among multiple stored PCEX translations, and choose source, replacement, or bilingual rendering
  with `RenderMode`.
