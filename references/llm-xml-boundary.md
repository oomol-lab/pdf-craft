# LLM XML 编解码边界

**约束范围：** 所有 LLM 请求与响应中的 XML 内容，包括分析、提取、翻译工程 fill、
首次请求、修复请求、上下文、工具返回，以及批请求或 JSON 字符串中的 XML 载荷。
这是统一的模型编解码边界，不以具体业务或模型供应商为例外。

## 统一输入与输出

- XML 输入：从已解析的结构调用共用 `encode_friendly` 生成模型实际看到的 XML。
  从文件读取的 XML 先解析，再编码；不能直接发送原始文件字符串，也不能先标准序列化
  再将结果当普通文本重复编码。文本与属性都由共用编码器处理。
- XML 输出：模型返回的 XML 必须通过共用 `decode_friendly` 解析，随后对结构化结果
  进行业务处理和既有校验。若外层是 JSON 批响应，先解析外层，再对 XML 字段执行此步骤。
- 使用当前共用实现 `pdf_craft/transformer/xml_translator/xml/friendly/`，不得在业务路径
  另写转义器、实体解码器或以直接 `ElementTree.fromstring` 等标准解析绕过该边界。
  共用编解码器能力不足时修复共用实现，并验证文本与结构往返，不添加业务专用替代路径。
- 持久化 XML、读取 PCEX/OCR 文件和其他非模型间的标准 XML 交换，继续使用标准 XML
  编解码；friendly 约束针对模型边界，不替换存储格式。

## 文本与结构不可混淆

friendly 是共用的模型表示协议，不承诺消除所有实体转义。当前协议需要通过转义区分
真正结构、字面量 `<span>`、字面量 `&lt;span&gt;` 和普通 `&`；不能为了可读性直接
取消 `&` 转义，或在整个输入上无条件、重复执行实体解码。
输出先识别结构，再按共用协议对文本及属性解码，不能让字面标签变成新增结构。
程序业务比较使用解析后的内容，不将序列化实体拼写当作原文字符。

该规则不会自动解决 XML 输入与 JSON 证据输出之间的表示差异。
不需要 XML 结构的业务可以用 JSON 承载解析后的纯文本，并让模型输入与证据校验
使用同一份文本。JSON、普通文本不因为包含 `&`、尖括号或字面 XML 示例就自动成为
XML 输出；按业务协议选择编解码方式，不靠回答内容猜测协议。

## 不改变业务权限

friendly 编解码只处理表示与结构，不新增业务语义门禁，不授予邻页或初级结构验收权限。
翻译 LLM 的自由表达约定保持不变：不能要求艺术家返回 XML，也不能因为其自由回答
不满足 XML 协议而拒绝或要求重译。工程 fill 使用 XML 协议时才执行对应编解码，
结构与完整性验收仍由 fill 层承担。

修改相关路径时，在真实请求边界验证 friendly 编码和解码确实被调用；覆盖文本与 tail、
属性、普通 `&`、字面标签、字面实体以及命名和数字实体的单次解码。
往返正确性与既有结构/全文校验必须同时成立，不能以测试通过为由跳过共用边界。
